# ADR-012 — Migrations SQL écrites à la main, réversibles par paires ; Drizzle est la vue typée

- Statut : proposée — 19 août 2026 (lot T-010)
- Source : `cadrage/STACK-TECHNIQUE.md` §3 (Drizzle ORM 0.45.2, PostgreSQL 18.6, pgvector 0.8.6) ;
  `cadrage/CAHIER-DES-CHARGES-FONCTIONNEL.md` §3 ; contrat T-010, critère « migration réversible »

## Contexte

Le contrat de T-010 exige des migrations **réversibles**, et pose que « réversible » se prouve :
appliquer, annuler, réappliquer, et constater que la base revient à un état identique.

`drizzle-kit` — l'outil de migration de Drizzle, 0.31.10 à ce jour — **ne produit pas de
descente**. Il génère un `.sql` de montée à partir de `schema.ts` et tient un instantané JSON ;
l'annulation n'existe pas dans son modèle. Une réversibilité qu'aucun fichier ne porte ne se
prouve pas : elle se raconte.

Trois faits secondaires ont pesé dans le même sens :

- `drizzle-kit` tire **trois copies d'esbuild** et impose une approbation de script d'installation
  (`ERR_PNPM_IGNORED_BUILDS`), qui fait sortir `pnpm install` en 1 tant qu'elle n'est pas
  arbitrée dans la configuration du gestionnaire de paquets.
- Le contrat de T-010 demande de **montrer** que la base refuse une violation d'unicité. Un SQL
  écrit à la main est lisible ligne à ligne par un relecteur humain ; un SQL généré ne l'est
  qu'après coup.
- Le schéma porte des contraintes que le vocabulaire de `schema.ts` n'exprime pas toutes — un
  déclencheur de refus de suppression (RG-STR-01), un index unique partiel (RG-STR-03), une clé
  étrangère composite auto-référente (RG-STR-05).

## Décision

1. **Les migrations sont des paires de fichiers SQL écrits à la main**, dans `base/migrations/` :
   `NNN_nom.montee.sql` et `NNN_nom.descente.sql`. La descente est l'inverse exact de la montée,
   sans `CASCADE` : une dépendance oubliée doit faire échouer l'annulation, pas emporter
   silencieusement un objet.
2. **`src/lib/base/schema.ts` n'est pas ce qui crée les tables.** C'est la description **typée**
   que l'application interroge — l'usage de Drizzle que la pile désigne, « accès SQL typé ».
3. **Un contrôle relie les deux.** `pnpm base:coherence` compare `schema.ts` au catalogue de la
   base réellement migrée : tables, colonnes, types de base, nullabilité. Sans lui, les deux
   descriptions du même objet dérivent en silence — c'est le seul risque réel que cette
   organisation introduit, et il est instrumenté.
4. **La réversibilité est prouvée par empreinte, jamais déclarée.**
   `pnpm base:reversibilite` monte, relève une empreinte structurelle SHA-256 du schéma `public`,
   descend tout, exige que le schéma soit **vide**, remonte, et compare les deux empreintes.
   `drizzle-kit` n'est pas installé.

## Ce que cette décision interdit activement

- **Créer une table hors migration.** Aucun `CREATE TABLE` dans le code applicatif, aucun
  `push` d'un schéma vers une base. La seule exception est le journal des migrations lui-même,
  créé par le lanceur : une migration qui créerait son propre journal ne pourrait pas s'annuler
  sans effacer la trace de son annulation.
- **Écrire une montée sans sa descente.** Le lanceur lit les deux fichiers ; une montée orpheline
  fait échouer `lireLesMigrations()`.
- **Corriger une migration déjà appliquée.** Le journal conserve l'empreinte SHA-256 du texte
  appliqué ; corriger le fichier fait mentir le journal. Une correction est une migration de plus.
- **Réintroduire `drizzle-kit generate`** sans réintroduire du même geste la production des
  descentes. Le jour où Drizzle sait annuler, cet ADR est à rouvrir — pas avant.

## Conséquences

- Le coût d'une évolution de schéma est le double : deux fichiers, non un. C'est le prix de la
  propriété demandée.
- `schema.ts` doit être tenu à jour à la main. `pnpm base:coherence` est ce qui rend cet oubli
  visible ; il fait partie de `pnpm verif:base`.
- Le contrôle de cohérence **ne regarde pas** les valeurs par défaut, le corps des contraintes
  `CHECK` ni les actions référentielles. Il attrape la dérive de structure, pas la dérive de
  comportement. Cette limite est imprimée par la commande elle-même à chaque exécution.
