# ADR-004 — Une seule implémentation document ⇄ Markdown

- Statut : acceptée — 18 août 2026
- Source : contrainte C-04 (`cadrage/STACK-TECHNIQUE.md` §1) ; RG-M13-01 ; STACK §4.3 et §4.6 ; `cadrage/PLAN-DE-REALISATION.md` §3.3

## Contexte

Le cahier des charges désigne l'export Markdown réimportable à l'identique comme le **« critère de réussite principal »** (RG-M13-01). C'est une propriété d'aller-retour : elle n'a de sens que si le chemin aller et le chemin retour sont le même code. Deux implémentations, même écrites avec soin, divergent au premier cas limite — un tableau imbriqué, un bloc d'alerte, une case de tâche — et la divergence n'apparaît qu'à l'import d'un export, c'est-à-dire chez l'utilisateur.

Le chemin d'import multiplie les tentations : le service Python de conversion retourne du Markdown, les fichiers `.md` et `.txt` entrent directement, et il paraît toujours plus simple d'écrire « un petit convertisseur pour l'import » que de réutiliser celui de l'export.

## Décision

Il existe **une seule** implémentation de la conversion `document ⇄ Markdown`, dans l'application. L'import l'utilise dans un sens, l'export dans l'autre. Elle est couverte par des tests de propriété portant sur **tout** le corpus.

Le service Python de conversion ne convertit **jamais** vers le document canonique : il retourne du Markdown et des images extraites, et l'application applique ensuite son unique convertisseur. Les fichiers `.md` et `.txt` ne passent pas par ce service et sont traités directement par l'application — c'est le chemin qui garantit l'idempotence et la résolution des références (RG-M12-01).

## Ce que cette décision interdit activement

- **Tout second convertisseur**, sous quelque forme que ce soit : fonction utilitaire d'import, chemin « rapide » pour les fichiers simples, transformation ad hoc dans un test, ou branche spécialisée par format d'origine.
- Les convertisseurs qualifiés de **« temporaires »**, **« provisoires »** ou **« pour l'import seulement »**. La qualification ne change rien à l'effet : la propriété d'aller-retour cesse d'être vraie dès qu'il existe deux chemins.
- **Toute conversion du document canonique effectuée hors de l'application** — en particulier dans le service Python, qui s'arrête à la production de Markdown.
- **Toute dépendance à une bibliothèque Markdown supplémentaire** dans le chemin d'import ou d'export : elle constituerait de fait le second convertisseur.
- **Toute correction appliquée d'un seul côté** de l'aller-retour. Un défaut de sérialisation se corrige dans l'implémentation unique, jamais par un rattrapage à la désérialisation.

## Conséquences

- L'import bureautique (`.docx`, `.pptx`, `.pdf`) et l'import Markdown convergent vers le même code après la sortie du service de conversion.
- Le **mode simulation** de l'import (RG-M12-02) est la même tâche exécutée dans une transaction annulée à la fin : un seul chemin de code, donc un rapport de simulation qui dit rigoureusement ce que fera l'import réel.
- L'arrêt du service Python dégrade l'import bureautique **sans empêcher** l'import Markdown (RG-NF-01, ADR-009).
- Toute nouvelle construction de contenu ajoutée au schéma ProseMirror (ADR-003) doit être traitée dans les deux sens de l'implémentation unique, sans quoi la batterie 4 rougit.

## Comment le vérifier

- **Batterie 4** — `pnpm test:aller-retour` : pour **tout** document du corpus, sérialiser puis désérialiser redonne le document d'origine. C'est la batterie nominale de cet ADR, et elle prouve la propriété, pas l'unicité.
- L'**unicité** elle-même n'a pas encore de batterie dédiée. Le contrôle existe pour la fraîcheur (batterie 5, `pnpm verif:fraicheur`) et doit être décliné à l'identique pour le convertisseur : un contrôle statique qui compte les implémentations et vérifie que tous les appelants passent par la même. À ouvrir comme extension de la batterie 5 ou comme batterie propre au lot d'export (M13).
